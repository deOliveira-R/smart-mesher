# W4-INT C12: the Linux x86_64 divergence of `w4_poly` and `w4_regions`

Ruling C12 (`docs/design/w3c/rulings.md:20`): on a cross-platform divergence of a milestone identity hash, fix the
near-tie decision locally first; a portable libm only if that fails; raw-bit hashes may stay per platform.
Start: PR #17 tip `5d6bb4b4b8f1ee07969d205a9076ff85d6947622` (15 `[linux-x86_64]` lines in `tools/platform/expected.txt`).

## Method

`collect.py` already records the state hash after every logged op (`node.NNN.state`). For each script the first
differing node between macOS and the Linux container was found, then the first differing f64 inside it, by
temporary instrumentation (removed before the commit; nothing of it is in the tree): per-op word streams of the model
hash (`HashWord` raw bits and quantized code), `Set pcurve` traces, per-mesh coordinate and connectivity dumps, the
pave and tri kernels' outputs, and per-stage dumps of the tet pipeline.

## (B) `w4_regions`

First differing op: node 22, the **ninth `model.subdivide_pin`** (nodes 0 to 21 are equal on both, including
`model.rotate`). The reviewer's lead (`model.rotate` by 57.2957795 degrees, `SEAM_TURN.cos()/sin()`) is **refuted**:
the bits of `cos`/`sin` of 1 rad and of every sector angle `phi` printed in `cut_pin` are identical on both platforms
(`d = 3fe14a280fb5068c,3feaed548f090cee` and the tool frame x vector equal).

The first differing f64 is the **cut centre** the script passes in: `center: [c[0], c[1], 0.0]` where `c =
model.measure(entity: v).centroid`. The centroid of a pin is a quadrature (`volume_moments`, Gauss samples of the
cylinder through `sin`/`cos`). For the first pin the origin x is `0x3cc6ca60278c975d` (1.1e-17) on macOS and
`0x3cc68c00b0a5c316` (1.0e-17) on Linux; the analytic value is 0. Every pin's centre carries such noise (1e-17 to
1e-16), different per platform.

How it reached the hash: the noisy origin makes a seam point of a cut loop project to `u = 0` (macOS) or to
`2 pi - ulp` (Linux) in `pcurves::fix_face`, and the loop is unrolled from one branch or the other: a `Line2` pcurve
with origin `u = pi` on macOS and `3 pi` on Linux (words 37268..., `W F 400921fb54442d18` against `4022d97c7f3321d2`).
That is a different quantized code, so `h_model` moved. Later the same noise reached the O-grid/pave faces: after the
model hash was made equal, `h_linear` still differed because the boundary `(u, v)` of the 3-sided sector faces differ
by a few ulp, the exact in-circle predicate of the pave CDT turns that into a different flip of exactly cocircular
nodes, and the quads of 2 of the 36 sector faces came out in another order.

### Fix (local, in `sm-model`, 1 file)

`crates/sm-model/src/queries.rs`, `model.measure`: the reported centroid is rounded to a power of two, 2^-42 (2.3e-13)
for the default tolerance (the power of two at most the hash quantum `linear * 2^-10`, divided by 4096), so a dyadic
centre such as 1.0, 2.0, 3.0 stays exact. The noise is about 1e-16, the pin centres 1.26 and 2.52 sit 4 percent of a
step from a grid point (no rounding tie), the shift is below 1.2e-13, and no libm is needed. A first try with the
hash quantum itself (2^-30) shifted the cuts by up to 4.7e-10 and broke the 1e-12 exact-volume assertion of
`milestone_w4_regions`; that is why the step is 2^-42. With it alone
(no change in `sm-boolean` or the schemes) the unchanged `w4_regions.smesh` gives one value on macOS arm64, Linux
arm64 and Linux x86_64 for every row (`h_model`, `h_auto`, `h_linear`, `h_mesh`, state, layers, branch, mem).

Tests: `crates/sm-model/tests/queries.rs::measure_centroid_lies_on_the_quantum_grid_and_is_the_analytic_centre`; the
macOS arm64 digests `MAC_SMSH` and `MAC_SMRT` of `crates/sm-cli/tests/milestone_w4_regions.rs` move with the model
(`lattice.smsh` `9353bb26...` to `bcfa82dd...`, `lattice.smrt` `efef863b...` to `ae4ec9f1...`; the test only checks them
on macOS arm64).
`model.measure` is the only reader of centroids among the pinned scripts (`grep centroid tools/*.smesh`), so no
older row can move; the census below confirms it.

Not used (kept out because they moved older rows, see "Held changes"): a seam snap in `pcurves::fix_face`, a banded
in-circle in the pave CDT.

## (A) `w4_poly`: blocked on `sm-geom-api`

`h_model`, `h_sized`, `h_auto` are equal; the first divergence is `mesh.run` (`h_tet`), per volume:

1. Input points of the tet pipeline (`SurfaceInput.points`, 3461 for the whole run): **169 differ by 1 ulp** between macOS
   and Linux, for instance `TopoEdge#22` node 5: `3fd04cf39b865544` (macOS) against `3fd04cf39b865545` (Linux), and
   `TopoFace#16` interior nodes. The edge nodes are circle points: `Circle::eval` calls `t.sin_cos()`
   (`crates/sm-geom-api/src/analytic.rs:130`; `Cylinder`, `Sphere` and the others do the same at lines 26, 356, 370, 421).
   The face nodes follow from them.
2. Because the circles' symmetric nodes are cocircular (and the pin's rings cospherical) in exact arithmetic, the
   ulp-level input difference changes the exact Delaunay decisions: the first stage of the tet pipeline already
   differs (9554 against 9562 tets in one volume; one volume has 1721 against 1722 input points because the tri
   refinement queue ties break differently). Later stages (heap order by badness, respace) are affected the same way.

The source is the platform libm in a **frozen** contract crate, so the rule is not to work around it. Decision-level
fixes were tried and are not acceptable (see "Held changes"): each either moves older pinned rows or breaks an
invariant.

### api_change_request

* What: `crates/sm-geom-api/src/analytic.rs`: evaluate `sin`/`cos` of curve and surface parameters through a portable
  libm (the `libm` crate, version-pinned) in `Circle`, `Ellipse`, `Cylinder`, `Cone`, `Sphere`, `Torus`
  `eval`/`jet`/`project` and the helpers at lines 26, 130, 268 to 286, 356 to 421 (a `util::sincos(x)` wrapper keeps it
  to one place).
* Why: the bits of every curve point differ between macOS and glibc by 1 ulp; exact predicates in the meshers turn
  that into different meshes (C12 rung 2: a local decision fix is not available because the decisions are exact
  predicates on cocircular and cospherical points shared with older pinned rows).
* Proposed signature: no public signature change; add `libm = "0.2"` to `crates/sm-geom-api/Cargo.toml` and
  `pub(crate) fn sincos(x: f64) -> (f64, f64)` in `util.rs`.
* Cost: this moves coordinate bits on **every** platform for every row that evaluates a circle or cylinder (macOS and
  glibc both change to the libm crate's result), so W2 to W3c rows can move; it needs the user's C3 decision and a
  census refresh. It would also remove the per-platform `flat_golden` bundle hashes only if they depend on it (they
  are raw-bit hashes and may stay per platform).

## Notes for later tasks

* The fixed point is "a script input that is a measured float must not carry libm noise"; any other script that feeds
  `model.measure` centroids (or `bbox`, `length`, `area`, `volume` quadratures) back into an op has the same exposure.
* Expect the pave and tri kernels to stay noise-sensitive wherever symmetric (cocircular) nodes come from a
  libm-evaluated circle; the real cure is the `sm-geom-api` request above.
