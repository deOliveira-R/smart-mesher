# W4 rulings (user, 2026-11-09)

These answer `plan.md` section 9 (D1-D10) and override the plan and drafts where they differ. The W3b and W3c rulings in plan section 2 still bind, including the standing principle: Cubit and legacy codes are bars to surpass, not specs to match.

## Answers
- **D1. Cells for the transport code:** target planar convex cells (what ray tracing wants too) and accept any polyhedron, including hexes, wedges and pyramids in one mesh. Both pin modes are built; `ogrid` goes into `hex_only`. So W4-POLY-MIXED runs in a3 and HEX-PYR stays in W4c. Orthogonality is a goal, not a hard requirement: VORO-CLIP/CONFORM stay trigger-based.
- **D2. File format:** the transport code reads `.smsh` first; `.smsh` is meant to be the best format. Every polyhedral export fills the geometry cache (`gc_*`) with no format bump. Fluent, CGNS and Abaqus writers stay in W4c for interchange. Importing other formats into `.smsh` is future work (W5, no trigger yet).
- **D3. Coarse-mesh acceleration:** the code is not written yet but will use CMFD/multigrid. ACR-LEVELMAP lands in W4-0b, W4-POLY-AGG in W4b with a per-pin mode; refinement levels are stored the same way (linked independent meshes).
- **D4. Round-region volume:** option (b): an opt-in op moves circle nodes to the equal-area radius so each material volume is exact at any interval count (VOLFIT in W4-MESHER-LISTS); VOLDIAG reports the deficit everywhere; (c), a volume-matched tessellation in `sm-tess`, is a W5 task. The pin milestone checks `pi r^2 h`.
- **D5. `ogrid` in `default`:** yes. The through pin, its lattice, B5 and the leftout fixture hashes move on purpose in one commit that lists every moved line; W2, W3a and W3b hashes stay. This is the only planned hash move in W4.
- **D6. Benchmark machine:** the user has a bare-metal x86_64 machine at work. It is not needed until W4a's ray-tracing rows and cell index have merged; then we deliver `tools/bench/x86_64.sh` (one command, Docker images, no network after the image pull) and the user runs three sessions. The polyhedral row is published as a separately labelled table, never in the k-of-n "beats XDG" verdict.
- **D7. Formats:** (a) STL import/export is future work: STL loses material identity and is already faceted, so it brings little now. W4-STL-IN and W4-STL-WIRE move to W5, with the trigger "a concrete need for STL input". (b) DAGMC `.h5m` straight from the B-rep: yes (ACR-DAGMC-SRC in W4-0, W4-DAGMC-MODEL in a1). (c) No existing `.h5m` models; we generate our own with OpenMC, DAGMC tools and our own exporter as needed. (d) IGES: W5+.
- **D8. Models:** the user's work models cannot be shared. Reference models come from public sources: OpenMC (its examples and our own decks), FreeCAD (via its MCP, for CAD and deliberately dirty STEP), the BEAVRS benchmark, and the INL Virtual Test Bed repository (public); MOOSE may be installed to turn its programmatic reactor geometry into geometry files. Matching these is the evidence that the user's own models will work. A new task W4-REFCORPUS builds the corpus (scripts committed, large files not; sha256 recorded). Hex lattices appear in these sources (Virtual Test Bed HTGR, SFR and microreactor models), so CSGBREP-HEX is scheduled in W4c with both orientations, each confirmed against OpenMC (C7), and the sm-rt hex lattice gains the second orientation (overrides W3b Q3's pointy-top-only limit). A local-model benchmark table is not planned, since there is no shareable local model.
- **D9. Regions per pin and per pin subdivision:** required as an option. A lattice element can be defined once ("all pins equal", one region) and the export asked to split it into one region per lattice position. Pins can also be subdivided (radial rings, azimuthal sectors) for depletion, so a split lattice gives lattice positions x subdivisions regions. This is lattice functionality: the lattice records each element's position, the subdivision records ring/sector indices, and the region split is an export option over both. Region names are structured (material, lattice position, ring, sector), and the same region split is written to `.smsh` cell sets (the transport code reads `.smsh`) and to `.smrt` regions. New task W4-REGIONS in W4a; any contract change is an ACR in W4-0.
- **D10. Defaults:** confirmed as listed (no GPU in W4; high-order and boundary layers in W5; OpenMC plugin in W5; circumcentric dual opt-in until W4-INT decides; `hex_only` suggests cuts; OpenMC import is one history node; many-to-one sweep in W5; optional Delaunay output in `sm-scheme-tet` if MEASURE needs it; no Fluent licence, OpenFOAM is the oracle).

## Process
- C3 carries over: any move of an existing hash other than D5's stops the task and goes to the user.
- A sub-wave merges only with GitHub CI green on its PR as well as the local run.

## Orchestrator rulings
Design calls with one-sided answers, made by the orchestrator (not user decisions; the user can veto any of them). They bind W4 workers.

- **sm-rt-bench and sm-poly.** `sm-rt-bench` may depend on `sm-poly` (library only) for the L2b polyhedral twin.
- **Conforming tet twin.** The conforming P1 tet twin is generated offline with the `smesh` CLI into the case directory, and its SHA-256 is pinned per os-arch. `sm-rt-bench` takes no `sm-mesher` dependency (`drafts/rt.md` risk 8).
- **Healing.** It lives in `sm-boolean`, tolerance first (raise per-entity tolerance, then weld or merge within it; geometry moves only on request). Collapse is virtual, with the gap bookkeeping of ACR-V3 (`drafts/vtopo.md` D3, D4).
- **Pre-registered win criteria.** A benchmark row is a win only if the agreement check passed for both trackers, the median rate is higher by more than the larger min-max spread at 1 thread and at the full physical-core count, memory and build time are shown beside it, and the sign holds in each of three independent sessions. Losses are published. The criteria are fixed in code before any real table exists (`drafts/rt.md` Q2).
- **Headline build.** The headline uses the default build for every tracker. A second sm-rt row built with `-C target-cpu=native` is published and labelled as such (`drafts/rt.md` Q5).
- **`renumber`.** It is not in the export selection (`drafts/export.md` D3). It can be added later as an opt-in key.
- **GPU smoothing and quality.** Not in W4 (user ruling D10). Trigger to revisit, from `drafts/export.md` D5: a measured smoothing or quality pass above a threshold the user names (for example more than 60 s at 10^7 cells on CPU), together with a GPU determinism rule the user approves.
- **OR-a (W4-0.3 part d): 2D lattice z.** Keep the existing lattice behaviour. For a 2D lattice (`dims[2] == 1`) the element centre z stays `origin.z + 0.5 * pitch[2]` (`bridge.rs:325` and sm-rt's `Lat::center` rely on it). The docs that say "z pitch ignored" are corrected to the actual rule and a test pins it. No behaviour change, no hash moves; `drafts/rt.md` W4-RT-LATZ is not built.
- **OR-b (W4-0.5): `source` in test literals.** The mechanical `source: Default::default()` / `ExportSource::Mesh` additions in existing test literals of `sm-server/tests` and `sm-cli/tests` are accepted (no asserted value changes). MCP and Python exposure of `source` is deferred to W4-DAGMC-MODEL.
- **OR-c (W4-0.6 / ACR-REGIONS): hash tags.** Tag 13 is already used by instancing clusters (`sm-model-api` `canonical.rs`). Lattice frames use tag 14 and region tags use tag 15, emitted only when non-empty, after the decomposition table.
- **OR-d (a1 review): XDG image is x86_64-only.** Upstream `vec3da.h` includes `immintrin.h`. On arm64 `docker-check` reports `Failed` with the reason and the rows are `Partial`; a Rosetta amd64 smoke run is allowed. Real numbers come from BENCH-X86.
- **OR-e (a1 review): checks in a sub-wave.** Workers run their own crates' checks (and those of the crates that depend on them); the combine runs `tools/ci.sh` once. Catalog goldens that only gain the entry of a newly registered op or query (`crates/sm-mcp/tests/golden/tools.standard.txt`, sm-py `ops.pyi` and stubs, the `sm-protocol` catalog) are re-blessed once by the combine, which lists the diff and checks it is exactly the new entries.
- **OR-f (a3): what the D5 move covers.** D5 names objects, not line numbers: the through pin, its lattice, B5 and the leftout fixture. Every test or script that pins one of these meshes (or an export of it) moves with them in the one D5 commit, even when R1 did not list the line: `crates/sm-server/tests/auto_select.rs` (pin, lattice, B5 rows), the macOS digests of `pin.smsh`/`pin.smrt` in `crates/sm-server/tests/regions_split.rs`, `tools/w3c_pin.smesh`, and the W4-era `crates/sm-decomp/tests/model.rs` enclosed-pin cell counts (decomposed, so `ogrid` now applies). The bound is the census: its diff must equal exactly the D5 rows (the `w3c_pin` platform rows except `h_model` and `layer.model`, the leftout rows, `pin.hexes`, and `expected.txt.sha256`), and W2, W3a, W3b and the enclosed pin row stay.
- **OR-g (a3): catalog descriptions.** OR-e extends to description and docstring text of an existing catalog entry when a merged task changed that op's documented behaviour (for example `mesh.to_poly` now takes mixed meshes). The combine re-blesses it and lists the changed lines; a changed signature or a removed entry is still C3.
