### Goal
Everything the W3b-RTBENCH plan promised runs on this Mac (Apple M1 Max, Docker Desktop, native linux/arm64, no qemu) as a `SMOKE RESULT`, so the x86_64 machine only needs `docker-check` plus `run`. Concretely: the three DAGMC-family images (`dagmc-moab`, `dagmc-dd`, `xdg`) build from pinned inputs, all three implement W-track, W-fire (hinted and located) and W-flight (surface tracking), results carry a real image identity, and the cross-checks (competitor vs competitor, competitor vs sm-rt facet twin, competitor vs analytic truth) run and pass. No ratio, speedup claim or committed number appears anywhere (rulings Q9, RTBENCH "Must NOT").

**Critique delta.** Q9 says the Mac run is smoke only. The firm W3c goal is BENCH-PIN: pinning, image identity, Docker hygiene and the small fixes. W-fire/W-flight in the DAGMC drivers (C) is a second step (stretch); the XDG image and driver (B) is stretch or W4; the tet walk is W4.

I cloned `pshriwise/xdg` (now `xdg-org/xdg`; 633 commits) on 2026-11-07 and `git cat-file -t 83efb306e152` fails. The tip is `fec8098` "Element walk updates (#250)", dated 2026-09-08 (it is the first commit with the element-walk and hex/quad support the plan wants). So the XDG image could never have built, regardless of architecture. The Dockerfile also clones `pshriwise/xdg` and `bitbucket.org/fathomteam/moab` tag 5.5.1, while the DAGMC images use conda MOAB 5.6.0; fairness rule (a) wants the same MOAB across rows.
   - **Critique delta:** the critique confirms the pin `83efb306e152` appears in both the Dockerfile and `docker.rs:19`. Correcting it is mechanical (the old pin never existed): pin `fec80980ce29` and MOAB 5.6.0 (fairness). No user question.
2. **XDG API is available and readable** (this is why the W3b note said "not available to check here"). `include/xdg/xdg.h`: `XDG::create(MeshLibrary::MOAB, RTLibrary::EMBREE)`, `prepare_raytracer()`, `find_volume(point, dir)`, `ray_fire(volume, origin, dir, dist_limit, HitOrientation, exclude_primitives*)` returning `pair<double, MeshID>`, `point_in_volume`, `find_element`, `next_element`. `include/xdg/mesh_manager_interface.h:46,58` `walk_elements(start_element, start, end|u,distance)` returns `vector<pair<MeshID,double>>`. CMake options (`CMakeLists.txt:4-11`): `XDG_ENABLE_MOAB/LIBMESH/GPRT`, `XDG_BUILD_TESTS`, `XDG_BUILD_TOOLS`; Embree 4.0.x..4.1 or 3.x is searched (`:55-59`). Upstream's own `Dockerfile` uses `ubuntu:24.04` with apt `libembree-dev`, which on noble/arm64 is Embree 4.x. XDG reads the DAGMC-style MOAB file (volume and surface entity sets with `GEOM_DIMENSION`, `CATEGORY`, sense tags: `src/moab/mesh_manager.cpp:132-197`).
   - Consequence 1: XDG's `ray_fire` row can reuse the **existing** `facets_to_h5m` output (`drivers/dagmc/facets_to_h5m.cpp`), so it needs no new converter.
   - Consequence 2: `smtets_to_moab` is only needed for the tet-walk row. It must write the tets in volume sets plus, per region pair, the interface and exterior triangles in surface sets with forward/reverse volume senses (XDG's tet file shape).
   - Open to verify while building: whether `XDG_GIT_SUBMODULE` forces `git submodule update` (GPRT is heavy and must stay off; prefer apt `libfmt-dev` and `XDG_BUILD_TESTS=OFF XDG_BUILD_TOOLS=OFF`).

An index digest is architecture-neutral, so the same pin works for arm64 now and amd64 later. Stale text: the comments in `src/docker.rs:4`, `pins.env` header, and the `UNSET` handling remain valid as guards. What really is **not** pinned: apt package versions in the xdg image (ubuntu `apt-get install`), conda solves of `dagmc-moab` and the mamba solve of the `dagmc-dd` fallback (floating on conda-forge), MOAB/DAGMC tags (tags, not SHAs). And `ResultFile::image_digest` (`src/result.rs:220`) is declared but **never assigned** anywhere in `src/cli.rs`, so no result file records which image produced it.
5. **Driver gaps** (`drivers/dagmc/dagmc_driver.cpp`): header comment line 15 and `main` (line 141 on) implement W-track only: one output row with `"workload":"w-track"` hard-coded (line 227). The Rust side already defines the other workloads (`adapter.rs:30-48`: `w-track`, `w-fire`, `w-fire-locate`, `w-flight`) and the exact W-fire and W-flight semantics: hinted fire = one fire per ray from the start state to the first region boundary, `Output.fires = (dist, to_region)`, with `-1` complement and `-2` lost (`adapter.rs:390-416`); flights = per-history `SplitMix64::for_index(seed, h)`, `tau = -ln(1-u)`, tally layout `[collisions per region | track length per region | leaked | absorbed]` in 256-history blocks, same blocks for every adapter (`adapter.rs:419-560`, `rng.rs`).
6. **The runner does not send what a flight needs to a container.** `docker::run_competitor` (`src/docker.rs:181`) passes only `SMRT_REPS`/`SMRT_WARMUP`, the case directory and thread counts: no histories, no seed, no sigma. Competitor rows with `workload != w-track` are appended unchecked in `src/cli.rs:235-256` (tracks only exist for W-track; no fire or tally dump is parsed). `compare_tallies` (`src/runner.rs:98`) exists and just needs a competitor `Output`. Track dump is emitted only for the first thread count (`run_case.sh`, `first=1`), which is fine.
7. **Analytic H1 and P2 tet twin** are limits of `smrt.rs`: `smrt.rs:195` (`a box inside a solid needs a union of half-spaces`) makes H1 `Unavailable` (4 boxes of 8 inclusions); `smrt.rs:269` / DESIGN "P2 has no tet twin" (pins stand in vacuum so no volume fills the box). 8. **P1 `facets` row at `tiny`** is `partial` because `twin::add_moderator` (called from `cases.rs:347`) emits zero-area triangles when the rings of `sag_pin = 1e-2` have coincident corners; `smrt.rs:52-76` (`zero_area`) refuses them. `reduced` and `full` have none. `tiny` is only a test scale.
9. **`--model` with imported periodic faces** fails because `sm-cadio` leaves pcurves unset (`DESIGN.md` Known limitations). Another crate; not for this task.
10. **`date_utc` and the sequence counter** are already out of every hash (`DESIGN.md` "Hashed output and the clock", test `two_smrt_runs_give_one_result_hash_and_date_and_sequence_stay_out_of_it`). The W3b-1 note is closed for sm-rt rows; what is missing is the same property for competitor rows (the driver prints `peak_rss_bytes` and `determinism`, `result_hash` covers non-timing fields), which the new acceptance covers.
11. **Docker Desktop on macOS is a Linux VM**: container `nproc`, memory, and CPU model are the VM's; the M1 Max has 8 P and 2 E cores. Governor is not visible. `bench-env.json` (`BenchEnv::detect`) records the host; it does not record the VM's CPU count. This must be logged or thread-scaling rows are unreadable.
12. `tools/conformance/dagmc/Dockerfile:13` uses `FROM condaforge/miniforge3:latest` (conformance, not the benchmark). Not touched here; mention in the report.

**C. W-fire and W-flight in the competitor drivers (M)** — BENCH-WORKLOADS (stretch)
- `dagmc_driver.cpp` and `xdg_driver.cpp` add `--workload track|fire|fire-locate|flight`. Fire: one fire per ray from the hinted start volume (hinted row); `fire-locate` adds `find_volume` / `point_in_volume` loop for the located row (DAGMC's stock `find_volume` is a linear loop over volumes: documented in the row note). Output `{"fires":[[dist,to_region],...]}` in ray order, to-region and lost codes as in `adapter.rs:406-413`.
- Flight: `--histories N --seed S --sigma path` where `run_case.sh` writes a plain `sigma.txt` (region id, sigma_t, sigma_a per line) from `smcase.json`'s regions by a tiny Rust-side helper in `docker.rs` (no JSON parser in C++), the driver reimplements `SplitMix64::for_index`, the `-ln(1-u)` flight sampling (`std::log`), isotropic rejection direction and the 256-history block tallies exactly as `adapter.rs`'s `history`. Output `{"tally":[...],"tally_sq":[...],"blocks":B}` plus counters (steps = fires, collisions, lost). Agreement: `compare_tallies` against the sm-rt facets (surface) adapter in the same group, 4 sigma.
  - **Critique delta:** a bit-identical SplitMix64 port is not required: the 4-sigma comparison is statistical, so an independent RNG explicitly seeded from `--seed` is simpler and still valid (determinism per CLAUDE.md: seeded from inputs). Keep the port only if correlated comparison is wanted; the worker states which in DESIGN.md.
- `run_competitor` gains `histories`, `seed`, `workloads` parameters (passed as `SMRT_HISTORIES`, `SMRT_SEED`, `SMRT_WORKLOADS`), parses the fire and tally lines into the same `Output` the sm-rt adapters produce, and `cli.rs` gets: fire agreement (hinted fire distances equal within `chord_tol`; `to_region` equal except grazing as in `compare.rs`), flight tally agreement, and the DAGMC-vs-XDG and moab-vs-dd region-sequence notes for every pair.
- The `C++ flight cannot be bit-identical to Rust` (`ln` and `sqrt` in libm vs libstd): the determinism assertion for competitors stays "observed" (`stable` across repetitions and across thread counts of the same driver), never asserted equal to sm-rt.

### Risks
- **XDG on arm64** (Embree 4.x from apt, `find_package(embree 4.0.0...<4.1.0)` with Embree 4.3 in noble is the likeliest failure; fallback: build Embree 4.0.x/4.3 from source with `EMBREE_ISA_NEON`) and submodule fetches (GPRT must stay off). Time-box it; the image stays `unavailable` with the failing command per the existing contract.
- **XDG tet file shape** may need surface sets that cover interior interfaces correctly; if XDG's ray tracer requires a watertight, oriented set, the converter must generate senses from region ids (`smtets` has `region i32 per tet`), which is nontrivial; mitigated by making it a separate milestone (**Critique delta:** W4).
- **C++ vs Rust flight statistics** use different libm, so tallies agree statistically (4 sigma at fixed seed) not bitwise; at a fixed seed the check is deterministic per platform but could land at 4.1 sigma on a platform; the acceptance uses the existing block-variance estimator and the same 4-sigma rule as sm-rt delta vs surface; if one slot fails on arm64 the worker must report the z value rather than loosen the threshold.
- **Docker Desktop timing noise** (VM, E cores, thermal throttling). Smoke only; no gate on time; the report states it.
- **Mixed-precision comparisons**: DAGMC-dd and XDG are Embree float-based; sequence disagreements at grazing contacts are possible and are listed, not hidden; the 20000-ray equality in item 5 may need the grazing allowance for XDG.
- **Image reproducibility**: apt packages are not frozen; documented, recorded in `versions.txt`; conda locks fix the DAGMC images.
- **Lock files for the dd source fallback**: the fallback path builds double-down and DAGMC from source with a tag (`v3.2.4`) and a short commit; the lock covers only conda parts; the source commits are verified by `git rev-parse` in the build already.
